I work at Wasmer. Wasmer Edge is a cloud hosting platform powered by WebAssembly; it can host this repository’s generated static site. References: [Wasmer Edge docs](https://docs.wasmer.io/edge/), [Git deployments](https://docs.wasmer.io/edge/git/).

This change was prepared with AI assistance (Anthropic's Claude); the testing described below was run locally, and I did not deploy it to Wasmer.

## Summary

This adds a short "Deploy" section to the README with a Deploy to Wasmer badge. The badge links to Wasmer's import page for this repository. It also adds a small root `Anybuild` file, which only Wasmer's builder reads, so the Yarn 4 install sees `.yarnrc.yml` before running.

- `README.md`: a new "Deploy" section between "Checks" and "Contributing". It holds the badge and fork-first guidance: fork, import your fork, and the import does not copy the repository into your account. It also says that canonical links come from `SITE_URL` in `src/app/pageMeta.js` and that `public/CNAME` names pgtune.leopard.in.ua, so a copy on another domain should change both.
- `Anybuild`: generated by `anybuild generate . --provider node-static` (Anybuild 0.33.1), with two edits:
  - added `node_install_requires_all_files = True`, plus a two-line comment explaining it;
  - set the app name to `pgtune` (the generator had used my local directory name).

  All other lines are generator output unchanged: `static_dir = "dist"`, yarn, vite, Node 24.

No app code, dependencies, lockfile, scripts or CI files change.

## Why this repository

PgTune is a calculator that runs entirely in the browser. `llms.txt` says nothing is sent to a server, and a configuration is fully described by its URL. Teams that tune PostgreSQL often want their own copy, for example an internal instance next to their infrastructure docs. Two outside PRs that run PgTune in a container were merged here (#61 "Docker", #100 "Created Dockerfile"). The current `Dockerfile` runs `yarn dev`, the Vite dev server. The deploy option here serves the production build instead: prerendered `/` and `/about`, hashed assets and the Workbox service worker, as static files.

The `Anybuild` file is needed for this repository specifically. Without it, Wasmer's builder detects the project correctly (Vite, yarn, `dist`). But it stages only `package.json` and `yarn.lock` for the install step, so Yarn ignores `nodeLinker: node-modules` and `yarnPath` from `.yarnrc.yml` and installs with Plug'n'Play. The later `yarn run build` then fails with "Couldn't find the node_modules state file". With `node_install_requires_all_files = True`, the whole source, including `.yarnrc.yml` and `.yarn/releases`, is present at install, and the build matches your CI.

## Testing

All tests ran locally against base commit `0208aa249d49f896e6167dad503a9594bcb0f771` plus this patch. I did not deploy to Wasmer.

- **Normal build:** Node 24.22.1 with the committed `.yarn/releases/yarn-4.18.1.cjs`, mirroring `deploy.yml`.
  - `yarn install --immutable` passed.
  - `yarn run build` passed: it wrote `dist/` with `index.html`, `about.html`, `sw.js` (20 precache entries) and `manifest.webmanifest`.
- **Builder plan (Anybuild 0.33.1):**
  - Base commit: detected node-static, framework vite, yarn, `static_dir` dist, install inputs `package.json` only.
  - Patched commit: "Using static Node.js provider declared in Anybuild", same provider and `static_dir`, `node_install_requires_all_files: true`.
- **Builder-step replay:** I re-ran the planned install and build steps locally, with Yarn Berry 4.18.1 on PATH.
  - Base: the install used PnP, then `yarn run build` failed with "Couldn't find the node_modules state file".
  - Patched: install and build both passed, and `yarn.lock` was byte-identical after install.
- **Static serving:** I served the replay output with native static-web-server 2.38.0. Wasmer runs its own WebAssembly build of static-web-server, which I did not test.
  - 200: `/`, `/about`, `/about.html`, `/sw.js`, `/manifest.webmanifest`, the hashed JS, CSS and SVG assets, `/llms.txt`, `/robots.txt`, and a full configuration URL with query parameters.
  - 404: a missing path.
- **Headless Chromium** (playwright-core 1.64.1 from your devDependencies):
  - On `/`, filling total memory with 16 shows `shared_buffers = 4GB` and updates the URL.
  - The service worker becomes active at `/sw.js`.
  - Loading `/about` directly returns 200 with the "How it works" title.
  - A shared configuration link renders the configuration.
  - There were no console errors, no failed requests, and no requests to other hosts.

## Limitations

- I did not deploy this to Wasmer. The badge opens Wasmer's import page for this public repository. It does not fork or copy the repository; to customize the site or get rebuilds on push, import your own fork.
- If the import page shows a different preset, select node-static (static Node build). I can't promise the live import picks up the declared `Anybuild` automatically.
- The build needs network access to the npm registry for the Yarn install.
- `SITE_URL` (canonical and link-preview URLs) and `public/CNAME` point to pgtune.leopard.in.ua. A copy on another domain should change them; `CNAME` is just a served file on Wasmer.
- The service worker has scope `/`, so the copy should be served at a domain root, not a sub-path. Production source maps are published, as on the current site.
- `/about` and `/about/` return `about.html` on native static-web-server 2.32.2 and 2.38.0. 2.32.2 is the version Wasmer runs as WebAssembly, but I did not check Wasmer's runtime itself.
- `.nojekyll` and the GitHub Pages workflow don't affect Wasmer; nothing about the existing Pages deployment changes.
