Date: 2026-10-22

static-web-server (local runner): 2.38.0
Test subject: `TailAdmin/free-react-tailwind-admin-dashboard` @ `e888dd1716b9803b535c7c2fa4f2c6b7d39b3da9`
(npm + `package-lock.json`, Vite 8, `react-router` `BrowserRouter` with `/profile`, `/calendar`, `/basic-tables`, `/signin`, and a `*` 404 route).
I picked it over `satnaing/shadcn-admin` because shadcn-admin is pnpm-only (`pnpm-lock.yaml`), and pnpm hits the local builder's nested-temp problem.

## Verdict: WORKS on native SWS 2.38 (local runner only). NOT supported by the Wasmer runtime package as tested by root (wasmer/static-web-server@=1.1.0 = SWS 2.32.2 wasm, no --page-fallback). See the update at the end.

- On the local builder and local runner, a 6-line edit to the generated `Anybuild` file makes Anybuild's own serve command start static-web-server with the fallback page turned on. `/profile`, `/calendar`, `/basic-tables`, `/signin` and unknown deep paths then return **200 with index.html**. Headless Chromium renders the right React Router page on each one.
- Without the edit (negative control, same commit and build), the same deep routes return **404**.
- For `--runner=wasmer`, the same Anybuild file renders `SERVER_FALLBACK_PAGE="/opt/static_app/index.html"` into the artifact's `.env`. This is the correct runtime path, and the deploy code passes that file to `wasmer deploy --env-file`. I did **not** deploy, so it is unproven that Wasmer's `wasmer/static-web-server@=1.1.0` package reads `SERVER_FALLBACK_PAGE` at runtime. See the caveats.

## Minimal edit (exact diff)

```diff

+nodestatic_serve(
+    config,
+    build,
+    name = "tailadmin",
```

The essential change is a single keyword argument:
`extra_env = {"SERVER_FALLBACK_PAGE": build.static_app.serve_path + "/index.html"}`.

### Why this API surface (from the public stdlib)

- `node_static.bzl`: `nodestatic_serve(config, build, name = None, **overrides)` forwards to `staticfile_serve(..., provider = "node-static", **overrides)`.
- `staticfile.bzl`: `staticfile_serve(config, build, name = None, provider = None, **overrides)` builds the start string itself: `static-web-server --root={static_app.serve_path} --log-level=info [--config-file=...] --port={config.port}`. It then calls `serve(..., commands = {"start": start}, **overrides)`.
- `serve.bzl`: `serve()` accepts `env`, `extra_env`, `extra_commands`, `build_pre`, `build_post`, `mounts`, `volumes`, `cwd`, `prepare`, `services`. The comment above the last four calls them the "uniform user-facing override surface". `env` is `merged(merged(build.env, env), extra_env)`.
- `commands` cannot be passed: `staticfile_serve` already passes it, so you would get a duplicate keyword. Overriding `start` through `extra_commands` would also mean copying the generated start string. Setting an env var leaves the generated command untouched. SWS 2.38.0 maps `--page-fallback` to env `SERVER_FALLBACK_PAGE`.

### How the absolute path is derived

`build.static_app` is the `mount("static_app")` handle that `nodestatic_build` returns. A mount exposes `.path` (build-side path) and `.serve_path` (runtime path). Use **`.serve_path`**, not `.path`. `serve_path` comes from `EnvironmentLayout.serve_mount_path` in `crates/anybuild/src/internal/context.rs`:

- local runner: the build artifact dir, e.g. `<project>/.anybuild/local/build/opt/static_app`;
- containerized runners (docker, wasmer): `ContainerServeLayout`, which is `/opt/static_app` (`/app` only for a mount named `app`).

This is the same value `staticfile_serve` uses for `--root`, so the fallback always points at `<root>/index.html` wherever the artifact ends up. Observed values:
- local: `SERVER_FALLBACK_PAGE=/tmp/.../tailadmin/.anybuild/local/build/opt/static_app/index.html`
- `--runner=wasmer`: `.anybuild/wasmer/.env` contains `SERVER_FALLBACK_PAGE="/opt/static_app/index.html"`, and `wasmer.toml` maps `"/opt/static_app"` with `--root=/opt/static_app`.

## Caveats

1. **Asset-404 masking.** With the fallback on, every missing GET path returns 200 with index.html, missing hashed assets included (`/assets/nope.js` → 200 text/html). A browser that holds a stale `index.html` after a redeploy will then load HTML as JS. The failure is a silent white screen or a MIME-type error, not a 404. Crawlers and uptime checks also lose real 404s. This is the usual trade-off of SPA fallback, the same as Netlify `/* /index.html 200`. `HEAD` on a deep route still returns 404 (GET-only fallback), which may confuse some health or link checkers.
2. **`/404.html`.** If the app ships a real `404.html`, it is served normally. If it doesn't, the request falls back to index.html with status 200. SWS 2.38 also has a separate `--page404` option. This recipe does not use it.
3. **Absolute path.** Always use `build.static_app.serve_path`, never a literal or `.path`. On the local runner the two are equal. On docker or wasmer, `.path` is the build-side path and would be wrong at runtime.
4. **Deployed SWS is a different build.** On Wasmer, `sws_version = "2.38.0"` maps to the Wasmer package `wasmer/static-web-server@=1.1.0` (its `latest`, `2.38.0` and `0.1` all map to the same package, see `run/wasmer.rs`). I could not reach the Wasmer registry from here to confirm which upstream SWS it bundles, or that it reads `SERVER_FALLBACK_PAGE` from the app env. **One real Wasmer deploy that curls a deep route is still required before calling this WORKS for deployments.**
5. **Version coupling.** The edit depends on public stdlib internals: `nodestatic_serve`/`staticfile_serve` forwarding `**overrides`, `serve()` accepting `extra_env`, and the build struct exposing `static_app`. All of these are in 0.33.0 with `schema = 1`. The env var name comes from SWS (`SERVER_FALLBACK_PAGE`, present in 2.x), not from Anybuild. A future `schema` bump, a change to the `sws_version` → Wasmer package mapping, or a future native SPA option in the stdlib could make this redundant or break it. Keep `schema = 1` and `sws_version` exactly as `generate` emits them.
6. **Interaction with `_redirects`.** When the project has a `_redirects` file, `staticfile_serve` adds `--config-file=sws.toml`. The env var should combine with it, but I did not test that here because TailAdmin has no `_redirects`.
7. **Caching.** The fallback response carries `cache-control: public, max-age=86400` (SWS default for HTML here, same as `/`). This is not new, but it makes caveat 1 more likely after redeploys.

## Recommendation

- The mechanism is real and small. It uses only the public, documented override surface (`extra_env` on `nodestatic_serve` / `staticfile_serve`). It needs no custom server and no regenerate flag, and it changes no build steps.
- **Do not open campaign PRs with it yet.** First do one Wasmer deploy of a held history-router SPA with this exact edit, and confirm a 200 deep route and the rendered page on the live app (caveat 4). If that passes, the held history-router SPAs (TailAdmin react dashboard, shadcn-admin once the pnpm issue is handled, and similar) can be unblocked with the 6-line edit above.
- In each PR, keep the generated header, `schema` and `sws_version` exactly as generated. Add only the `extra_env` line with a one-line comment, and state the asset-404 masking trade-off in the PR description.
- If the Wasmer deploy shows that the fallback is ignored, the verdict becomes "local only". In that case the next lead is native SPA support in the public stdlib (for example a `staticfile_config` option), raised upstream instead of applied per repo.
